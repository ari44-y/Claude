## 1. 概要

自宅のサーバー（余っていたノートパソコン）上で動作する、生活サポート用の Web アプリケーション群。
外出先からスマートフォンでアクセスでき、複数のアプリが同時に稼働する構成とする。

### 1.1 前提条件

- サーバーはノートパソコン（Ubuntu Server）で稼働させる
- Web アプリとして提供し、スマートフォンのブラウザから利用する
- 外出先からもアクセスできる
- 以下のアプリを同一システム上で同時に稼働させる

### 1.2 アプリ一覧

| No. | アプリ | 状態 |
|---|---|---|
| 1 | タスク管理アプリ | 要件定義中 |
| 2 | 家電監視アプリ | 未定（スマート家電の導入後に検討） |
| 3 | 家計簿アプリ | 要件定義中 |

### 1.3 利用者

| 項目 | 内容 |
|---|---|
| 利用者 | 自分のみ |
| 影響範囲 | 複数ユーザー管理・タスクの担当者設定は不要 |

## 2. タスク管理アプリ

### 2.1 定期タスク

| 要件 | 詳細 |
|---|---|
| 定期実行の通知 | 定期的に行う必要があるタスクについて、スマートフォンに通知する |
| 対象例 | ゴミ出し、洗濯 |

#### 繰り返しルール

| パターン | 例 |
|---|---|
| 毎日 | 洗濯 |
| 毎週（曜日指定・複数可） | 毎週月・木：燃えるゴミ |
| 毎月第n曜日 | 第2・第4水曜：資源ゴミ |
| n日おき | 3日おき：植物の水やり |
| 毎月n日 | 毎月25日：家賃の確認 |

#### ゴミ出し

| 要件 | 詳細 |
|---|---|
| 収集ルール | 埼玉県戸田市 中町1丁目の収集ルールに基づいて、ゴミ出しタスクを登録・通知する |
| 出す時間 | 収集日 **当日の朝8時まで**。前日夜には出さない |
| 通知タイミング | 当日の朝8時より前に通知する（2.5 の「当日 7:00」に合わせる） |

**収集曜日（中町1丁目）**

| ごみの種類 | 収集曜日 | 主な対象 |
|---|---|---|
| もやすごみ | 毎週 水・土 | 生ごみ、製品プラスチック、汚れの落ちないプラマーク容器包装 など |
| もやさないごみ | 毎週 火 | プラマーク容器包装（すすいだもの）、ペットボトル（青いかご）、危険物（充電式電池・40cm未満の小型家電：透明な袋で赤いかご） など |
| 資源物 | 毎週 月 | 分別の詳細は戸田市「家庭ごみの正しい分け方・出し方」を参照 |

**収集の休み**

| 休止日 | 備考 |
|---|---|
| 11月23日（勤労感謝の日） | この日はタスク・通知を出さない |
| 12月31日〜1月3日 | この期間はタスク・通知を出さない |

- 上記以外の祝日は通常どおり収集する
- 出典：戸田市「令和8年度版 ごみ収集日一覧表」（令和8年4月発行）。年度ごとに変更の可能性があるため、毎年4月に最新版を確認して更新する

### 2.2 単発タスク

| 要件 | 詳細 |
|---|---|
| 手動追加 | 別途やるべきことが発生した場合に、自分でタスクを追加できる |
| 期限 | 任意で期限日時を設定できる |

### 2.3 買い物リスト

日用品の買い出しは、タスクとは別に「買い物リスト」として管理する。

| 要件 | 詳細 |
|---|---|
| ワンタップ表示 | スマートフォンのホーム画面からワンタップで買い物リストを表示できる |
| 実現方法（案） | 買い物リスト画面を、専用アイコンとしてホーム画面に追加する |
| 品目追加 | 買う物を1品ずつリストに追加できる |
| チェック | 買った物にチェックを付けて消し込める |
| 再利用 | よく買う物を履歴から再追加できる（案） |

### 2.4 カレンダー

| 要件 | 詳細 |
|---|---|
| 予定の登録 | 通常の予定を登録できる |
| リマインド | 予定とは別に、リマインドを個別に設定できる |
| タスク表示 | 期限付きタスク・定期タスクもカレンダー上に表示する（案） |

### 2.5 通知

| 要件 | 詳細 |
|---|---|
| 通知方式 | スマートフォンへのプッシュ通知（Web Push） |
| 通知の仕組み | タスクと予定の通知は同じ仕組みで扱い、通知の種類によって表示を変える |
| 通知タイミング（案） | 前日 21:00 と当日 7:00 の2回。タスクごとに変更できる |
| 予定の通知（案） | 予定の開始時刻の n 分前（予定ごとに設定）。種類は「お知らせ」として扱う |

#### 通知の種類

| 種類 | タイミング | 通知の例 |
|---|---|---|
| お知らせ | 事前（前日 21:00、当日 7:00 など） | 🗑️ 明日は燃えるゴミの日です |
| リマインド | 期限を過ぎても未完了のとき | ⚠️【リマインド】燃えるゴミ、まだ出してません！ 8時までです |
| リマインド（2回目以降） | 再通知のたび | 🔥【リマインド 2回目】いい加減やりましょう：燃えるゴミ |

#### リマインドの強調（「ちゃんとやれよ」感）

リマインドは、ひと目でお知らせと区別でき、放置しにくい表示にする。

| 工夫 | 詳細 |
|---|---|
| タイトル表示 | タイトルに【リマインド】と回数を付ける |
| 文面の段階的な強化 | 再通知の回数が増えるほど、文面をきつくする |
| バッジ | ホーム画面アイコンのバッジに、期限切れタスクの件数を表示し続ける |
| アプリ内の表示 | アプリを開いたとき、期限切れタスクを一番上に赤く表示する |

#### iPhone での制約

| 項目 | 内容 |
|---|---|
| 対応バージョン | iOS 16.4 以降 |
| ホーム画面への追加 | 必須。ホーム画面に追加したアプリからのみ通知を受け取れる |
| 通知の許可 | 画面のボタンをタップしたときにのみ許可を求められるため、初回に「通知をオンにする」ボタンを用意する |
| 通知音 | 独自の音は使えない（標準の通知音） |
| 通知上のボタン | 「完了にする」などのボタンは使えない。通知をタップしてアプリを開く |
| Tailscale との関係 | 通知は Apple の通知サーバー経由で届くため、Tailscale を接続していなくても受け取れる |

### 2.6 完了管理

| 要件 | 詳細 |
|---|---|
| 完了チェック | タスクを完了したら、チェックボックスなどで完了状態がわかる |
| 期限切れの再通知 | 期限を過ぎても未完了のタスクは、「リマインド」として一定間隔で再通知する（2.5 参照）。間隔は案 |
| 繰り越し（案） | 未完了の単発タスクは翌日に繰り越して表示する |
| 定期タスクの扱い（案） | 未完了でも次回分は通常どおり生成する（未完了分は期限切れとして残す） |

### 2.7 ゴミ分別チャット

「金属のフライパンは何ごみ？」のように、ゴミの分別をチャットで質問できるようにする。

| 要件 | 詳細 |
|---|---|
| 質問 | アプリのチャット画面に、ゴミの品目や出し方を自由な文章で入力する |
| 回答 | 戸田市の分別資料をもとに、「分別の区分」「出し方の注意」「次の収集日」を答える |
| 資料にない品目 | 推測で答えず、「資料にありません」と答える。市の公式情報の確認を促す |
| 回答の仕組み | サーバー上の Claude Code が、ルールと分別資料を書いた MD ファイルを読んで答える（6.2 参照） |
| 分別資料 | 戸田市の Web ページ「判断に迷う家庭ごみの分け方・出し方」（五十音順の品目一覧）と「家庭ごみの正しい分け方・出し方」を MD に書き写し、サーバーに置く。毎年4月に収集日一覧とあわせて更新する |
| 待ち時間の表示 | 回答に数秒〜十数秒かかるため、待っている間は「考え中…」と表示する |
| 分別検索画面（案） | 品目名で一覧から探せる検索画面。名前がはっきりしている品目を、Claude を使わずにすぐ調べられる |

## 4. 家計簿アプリ

### 4.1 機能一覧

| No. | 機能 | 概要 |
|---|---|---|
| 1 | レシート読み取り | レシートの写真から OCR で文字を読み取り、保存する |
| 2 | 手入力 | レシートがない支出も手入力で登録できる |
| 3 | カテゴリ分類 | 食費・日用品などのカテゴリで分類できる |
| 4 | カレンダー表示 | カレンダー形式で、日ごとに使った金額がわかる |
| 5 | 検索 | 過去に入力した内容を検索できる |
| 6 | 集計 | 月ごと・カテゴリごとの支出を集計する |

### 4.2 レシート読み取り（OCR）

| 要件 | 詳細 |
|---|---|
| 撮影 | スマートフォンのカメラでレシートを撮影する（撮影済み画像の選択も可） |
| 文字読み取り | OCR で画像内の文字を読み取る |
| 項目の抽出 | 読み取った文字から、日付・店名・合計金額を取り出して入力欄に反映する |
| 確認・修正 | 保存前に読み取り結果を確認し、誤りがあれば手で修正できる |
| 保存 | 確認後の内容を、レシート画像と合わせて保存する |

### 4.3 手入力

| 要件 | 詳細 |
|---|---|
| 手入力登録 | レシートがない支出（現金払い・振込など）を手入力で登録できる |
| 入力項目 | OCR と同じ項目（4.4）を入力する |

### 4.4 記録項目

| 項目 | 必須 | 備考 |
|---|---|---|
| 日付 | ○ | |
| 金額（合計） | ○ | |
| カテゴリ | ○ | 4.5 のカテゴリから選択 |
| 店名 | - | 手入力時は任意 |
| 品目明細 | - | 任意 |
| メモ | - | 任意 |
| レシート画像 | - | OCR で登録した場合に保存 |

### 4.5 カテゴリ分類

| 要件 | 詳細 |
|---|---|
| 分類 | 各支出をカテゴリで分類できる |
| カテゴリ例（案） | 食費、日用品、外食、交通費、医療、趣味・娯楽、衣類、光熱費、その他 |
| カテゴリ編集（案） | カテゴリの追加・名前の変更ができる |
| 自動推定（案） | 店名から過去に選んだカテゴリを初期値として提案する |

### 4.6 カレンダー表示

| 要件 | 詳細 |
|---|---|
| 日別合計 | カレンダーの各日に、その日に使った合計金額を表示する |
| 明細表示（案） | 日付をタップすると、その日の支出一覧を表示する |
| 月合計（案） | 表示中の月の支出合計をカレンダー上部に表示する |

### 4.7 検索

| 要件 | 詳細 |
|---|---|
| 検索 | 過去に入力した支出を検索できる |
| 検索条件（案） | キーワード（店名・品目・メモ）、期間、カテゴリ、金額の範囲。組み合わせて使える |

### 4.8 集計

| 要件 | 詳細 |
|---|---|
| 月次集計 | 月ごとの支出合計を表示する |
| カテゴリ別集計 | カテゴリごとの内訳を表示する（グラフ表示は案） |

## 5. 非機能要件

### 5.1 セキュリティ

| 要件 | 詳細 |
|---|---|
| 外部アクセス | Tailscale（VPN）経由に限定し、ルーターのポート開放は行わない |
| ログイン認証（案） | 不要。利用者が自分のみで、Tailscale により自分の端末以外からは接続できないため |

### 5.2 データ保全

| 要件 | 詳細 |
|---|---|
| 自動バックアップ | データベースとレシート画像を定期的に自動バックアップする |
| 頻度・保存先（案） | 毎日1回。保存先は外付けUSBストレージまたはクラウドストレージ |
| 保存先の理由 | ノートパソコン本体のストレージの故障に備え、本体とは別の場所に保存する |

### 5.3 利用環境

| 要件 | 詳細 |
|---|---|
| 対応端末 | iPhone（主、iOS 16.4 以降）、PCブラウザ（副） |
| PWA 対応 | ホーム画面に追加してアプリのように使える。iPhone で Web Push 通知を受け取る前提として必須 |
| HTTPS | Web Push の前提として必須。Tailscale の HTTPS 機能（`tailscale serve`）で用意する |
| 稼働 | サーバーの再起動後も自動で起動する（Docker の `restart: unless-stopped`。Docker 自体は OS の起動時に立ち上がるよう設定する） |
| ふたを閉じた状態での稼働 | ノートパソコンのふたを閉じてもスリープしない設定にする（`/etc/systemd/logind.conf` の `HandleLidSwitch=ignore`） |
| 停電への備え（案） | ノートパソコンのバッテリーが無停電電源の代わりになる。バッテリーの劣化・膨張がないか定期的に確認する |

## 6. 技術構成

```
┌──────────── iPhone ─────────────┐
│  PWA（React + TypeScript）           │
│   ├─ タスク / カレンダー / 買い物リスト  │
│   └─ Service Worker（通知の受信）      │
└──────┬──────────────▲────────┘
       │ 画面操作         │ プッシュ通知
       │（Tailscale・HTTPS）│（Apple の通知サーバー経由）
┌──────▼── サーバー（ノートPC・Ubuntu Server）──┴──┐
│  Tailscale（本体に直接インストール）                  │
│    └─ tailscale serve：HTTPS → 127.0.0.1:8000     │
│  ┌─ Docker コンテナ（kuroko-app）──────────┐    │
│  │  FastAPI（1プロセス）                     │    │
│  │   ├─ Web API                           │    │
│  │   ├─ 画面ファイル（React のビルド結果）の配信  │    │
│  │   └─ スケジューラー（1分ごと）               │    │
│  │        ├─ 定期タスクの生成                   │    │
│  │        └─ 通知の送信                        │    │
│  │  Claude Code（チャットの回答・Phase 2）      │    │
│  └──────────┬──────────────────┘    │
│     /data にマウント│                               │
│  /var/lib/kuroko：SQLite・レシート画像               │
│  systemd タイマー：毎日のバックアップ                  │
└──────────────────────────────────────┘
```

| 区分 | 技術 | 選定理由 |
|---|---|---|
| ハードウェア | 余っていたノートパソコン | 手持ちの機材を活用する。ストレージは SSD が望ましい |
| OS | Ubuntu Server | 画面なしで軽く動き、常駐サーバーに向いている |
| フロントエンド | React + TypeScript 5.9（Vite でビルド）、Node 26 LTS | 学習価値が高く、ライブラリが豊富。型によって API とのやり取りの誤りに気づきやすい。TypeScript 7 は openapi-typescript が対応していないため 5.9 にする |
| 見た目（CSS） | Tailwind CSS v4 | クラス名がほぼ CSS に対応しており、CSS の考え方も身につく。必要な部品が出てきたら shadcn/ui で足す |
| カレンダー表示 | FullCalendar（React 版） | 月・週・日表示を備えたカレンダーを簡単に組み込める |
| PWA 化 | vite-plugin-pwa（`injectManifest` モード） | ホーム画面への追加と Service Worker を簡単に用意できる。通知を受け取る処理を自分で書くため、Service Worker を自動生成しないモードを使う |
| 画面の切り替え | React Router | `/tasks`、`/shopping`、`/chat` などの画面を URL で切り替える |
| データの取得 | TanStack Query | サーバーからの取得・更新と、読み込み中や再取得の処理を任せられる |
| API の型 | openapi-typescript ＋ openapi-fetch | FastAPI が出す API 仕様から TypeScript の型を自動で作り（`npm run gen:api`）、画面とサーバーの食い違いに気づけるようにする。openapi-fetch はその型を使って API を呼ぶ |
| 画面のチェック・テスト | oxlint、Vitest | Vite の公式テンプレートの構成に合わせる |
| バックエンド | Python / FastAPI | 軽量で、手持ちのノートパソコンでも十分に動作する |
| DB の操作 | SQLAlchemy | Python から DB を扱う定番のライブラリ |
| DB の変更管理 | Alembic | テーブルを後から変えたときに、サーバーの DB を安全に作り替えられる。家計簿などを後から足すため必須 |
| Python のパッケージ管理 | uv | 開発 PC とサーバーで同じバージョンのライブラリを使える（`uv.lock`） |
| 実行環境 | Docker / Docker Compose | Mac（開発）と Ubuntu Server（本番）で同じ環境を再現できる。サーバーに Python や Node を直接入れずに済む |
| スケジューラー | APScheduler（FastAPI と同じプロセス） | 定期タスクの生成と通知送信を行う。1プロセスにまとめて SQLite の書き込み競合を避ける |
| 繰り返しの計算 | python-dateutil（rrule） | 「第2・第4水曜」などの複雑な繰り返しを計算できる |
| 通知送信 | pywebpush（Web Push） | 追加のアプリや外部サービスが不要 |
| データベース | SQLite | DBサーバーが不要で、バックアップもファイルのコピーで済む |
| 外部アクセス | Tailscale（`tailscale serve` で HTTPS） | ポート開放なしで安全に接続でき、証明書も自動で用意される |
| 常駐 | Docker の `restart: unless-stopped` | サーバーの再起動後に、コンテナを自動で起動する |
| バックアップ | systemd タイマー（サーバー本体） | 毎日、`/var/lib/kuroko` の DB と画像を外付けストレージなどにコピーする。保存先が本体側にあるため、コンテナではなく本体で実行する |
| チャットの回答 | Claude Code（`claude -p` で呼び出す） | ルールと資料を MD に書いておくだけで、そのとおりに答えさせられる（6.2 参照） |

処理の流れは [シーケンス図](シーケンス図.md) を参照。

### 6.1 データ設計の骨格（タスク管理）

定期タスクは「繰り返しのルール」と「各回の実体」を分けて持つ。完了チェックは各回に付ける。

| テーブル | 中身 | 例 |
|---|---|---|
| `task_templates` | 定期タスクの定義と繰り返しルール | 燃えるゴミ：毎週水・土 |
| `task_instances` | 1回分のタスクと完了状態 | 10/29(水) 燃えるゴミ：未完了 |
| `skip_dates` | 休止日。グループ名でテンプレートと結びつける（ゴミ出しの休止日は洗濯には効かない） | gomi：11/23、12/31〜1/3 |
| `events` | カレンダーの予定 | 11/3 14:00 歯医者 |
| `reminders` | 通知予定と種類（お知らせ / リマインド）。タスク・予定のどちらにも付けられる | 前日 21:00、当日 7:00 |
| `shopping_items` | 買い物リストと購入済みチェック | トイレットペーパー：未購入 |
| `push_subscriptions` | 通知の送り先端末の登録情報 | iPhone 1台 |

- 繰り返しルールは RRULE 形式（例：`FREQ=MONTHLY;BYDAY=2WE,4WE`）の文字列と起点日で持つ
- 日時は DB に UTC で保存し、計算と表示は日本時間で行う
- スケジューラーが毎日、繰り返しルールから2週間先までの回を作る（休止日は作らない）
- テンプレートを変更したら、今日以降の未完了の回だけ作り直す（完了済み・期限切れの回は残す）
- 列の定義は `backend/app/tasks/models.py`、解説は [解説 01](解説/01-バックエンドの土台とタスクAPI.md) を参照
- 1分ごとに通知時刻を過ぎたものを探し、未完了のものだけ送信する

### 6.2 Claude 連携（チャットの回答）

チャットの回答は、API のコンテナの中に入れた Claude Code に任せる。答え方のルールと参照する資料は MD ファイルに書き、アプリごとにフォルダを分ける。

#### フォルダ構成

リポジトリの `kuroko/` フォルダを、コンテナの `/opt/kuroko/` に読み取り専用でマウントする（Phase 2 で compose.prod.yaml に追加する）。MD を直して `git pull` するだけで、Claude の答え方に反映される（コンテナの作り直しは不要）。

- API から `claude -p` を呼ぶため、Claude Code は API と同じコンテナに入れる（Dockerfile でインストールする）
- Claude Code のログイン情報は、API キーを `.env` で渡すか、ログイン情報のフォルダをボリュームで渡す（9章の未決事項）

```
/opt/kuroko/
├── CLAUDE.md                 ← 共通ルール（すべてのアプリに効く）
├── task/                     ← タスク管理アプリ
│   ├── CLAUDE.md             ← ゴミ分別チャットのルール
│   └── gomi-bunbetsu.md      ← 戸田市の分別資料（市の Web ページから書き写し）
├── kakeibo/                  ← 家計簿アプリ
│   ├── CLAUDE.md             ← カテゴリ判定のルール（案）
│   └── categories.md         ← カテゴリ一覧
└── kaden/                    ← 家電監視アプリ（未定）
    └── CLAUDE.md
```

- Claude Code は、起動したフォルダの `CLAUDE.md` に加えて、上のフォルダの `CLAUDE.md` も読み込む。そのため共通ルールは `/opt/kuroko/CLAUDE.md` に1回だけ書けばよい
- アプリは、質問を受けた画面に応じて実行するフォルダを切り替える
- 1つのチャットで全アプリの質問を受けたくなったら、フォルダ分けをやめてスキル（`.claude/skills/`）に移行する

#### 呼び出し方

```python
FOLDERS = {
    "task": "/opt/kuroko/task",
    "kakeibo": "/opt/kuroko/kakeibo",
}

proc = await asyncio.create_subprocess_exec(
    "claude", "-p", question,
    "--allowedTools", "Read",
    "--output-format", "json",
    cwd=FOLDERS[app],
    stdout=asyncio.subprocess.PIPE,
    stderr=asyncio.subprocess.PIPE,
)
stdout, _ = await asyncio.wait_for(proc.communicate(), timeout=120)
answer = json.loads(stdout)["result"]
```

- `subprocess.run` ではなく `asyncio.create_subprocess_exec` を使う。回答を待つ十数秒のあいだも、ほかの API やスケジューラーの通知が止まらないようにするため

| 項目 | 内容 |
|---|---|
| 許可する操作 | `--allowedTools "Read"` でファイルの読み取りだけを許可する。コマンドの実行やファイルの書き換えはさせない |
| 質問の渡し方 | 引数のリストとして渡す（`shell=True` で文字列をつなげない）。質問に記号が含まれていても、余計なコマンドが実行されないようにするため |
| タイムアウト | 120秒で打ち切り、「時間がかかりすぎました」と表示する |
| 同時実行 | 利用者は自分ひとりなので、同時に複数の質問は来ない前提とする |

#### 配置と更新の手順

1. 開発 PC でリポジトリの `kuroko/` 内の MD を編集し、コミット・プッシュする
2. サーバーで更新スクリプトを実行する（7.5 参照）
3. サーバーで `docker compose -f compose.prod.yaml exec -w /opt/kuroko/task app claude -p "フライパンは何ごみ？" --allowedTools "Read"` を実行し、ルールどおりに答えるか確認する

### 7.4 サーバーでの動かし方

```
Tailscale（HTTPS・本体） ──▶ 127.0.0.1:8000 ──▶ コンテナ kuroko-app
                                                 └─ uvicorn :8000（FastAPI 1プロセス）
                                                      ├─ API
                                                      ├─ 画面（/app/frontend/dist）
                                                      ├─ スケジューラー
                                                      └─ チャット ──▶ claude -p（/opt/kuroko/task）
```

| 項目 | 方針 |
|---|---|
| プロセス数 | 必ず1つ（`--workers 1`）。2つにするとスケジューラーも2つ動き、通知が二重に届くため |
| タイムゾーン | スケジューラーに `Asia/Tokyo` を明示する。サーバーの設定に左右されないようにするため |
| 秘密の値 | VAPID 鍵（通知用の鍵）などは `.env` に置き、Git には入れない |
| データの置き場所 | DB とレシート画像はサーバー本体の `/var/lib/kuroko/` に置き、コンテナの `/data` にマウントする。コンテナを作り直しても、`git pull` しても消えないようにするため |
| ポートの公開 | `127.0.0.1:8000` だけに公開する。Docker が公開したポートは ufw（ファイアウォール）を素通りするため、`127.0.0.1` を付けないと家の LAN から直接開けてしまう |
| DB の作り替え | コンテナの起動時に `alembic upgrade head` を自動で実行する |

### 7.5 サーバーへの反映

Mac で開発して GitHub に push し、サーバーで pull して Docker で動かす。サーバーにもリポジトリを置き（`git clone`）、更新スクリプトを実行するだけで反映されるようにする。手作業のコピーはしない。

```
Mac ──git push──▶ GitHub ──git pull──▶ Ubuntu Server ──docker compose up -d --build──▶ 起動
```

```bash
# deploy/update.sh（サーバーで実行）
git pull --ff-only
docker compose -f compose.prod.yaml up -d --build   # イメージを作り直して入れ替え
docker image prune -f                               # 古いイメージを消す
```

- イメージはサーバーで作る（Mac は arm64、サーバーのノートパソコンは x86_64 で、CPU の種類が違うため）
- サーバーの初期設定（Tailscale の HTTPS、バックアップのタイマー、ふたを閉じてもスリープしない設定など）は [解説 04](解説/04-サーバーの準備.md) の手順書を参照
- バックアップは `deploy/backup.sh` を systemd タイマー（`deploy/systemd/`）で毎日 3:30 に実行する。保存先が決まるまでは `/var/backups/kuroko`（本体の中）に保存する

### 7.6 開発の進め方

| 場所 | やること |
|---|---|
| 開発 PC（Mac / Windows） | `docker compose up` で API（:8000）と画面の開発サーバー（:5173）をコンテナで動かす。ソースコードは PC のフォルダをコンテナに見せ、保存すると自動で読み直される。Vite の開発サーバーから FastAPI へ API を中継する |
| サーバー | 通知（HTTPS が必要）と、iPhone での動作を確かめる |

Phase 1 は次の順に作る。

1. タスクの API と DB（単発タスク → 定期タスクと繰り返しの計算）
2. タスクの画面
3. サーバーへの反映（Docker、Tailscale、更新スクリプト、バックアップ）
4. Web Push の通知（実機の iPhone で確認）

- 繰り返しの計算（第2・第4水曜、休止日など）は間違えやすいため、最初からテストを書く
- 改行コードは `.gitattributes` で LF にそろえる（Windows で CRLF になると、Linux のコンテナやサーバーでシェルスクリプトが動かないため）
- Windows では、リポジトリを WSL2 の中（`\\wsl$\Ubuntu\home\...`）に clone し、VS Code の WSL 拡張で開く（`C:\` に置くと、保存しても自動で読み直されないことがあり、動作も遅いため）
- 開発用の DB は PC ごとの Docker ボリュームにあり、Mac と Windows で共有しない
